# SOLID Principles & Design Patterns

## SOLID Principles

### 1. Single Responsibility Principle (SRP)

- A class should have only one reason to change.
- Every class should do exactly one thing. If it handles more than one concern, split it up.
- In Spring Boot, `Controller` handles HTTP, `Service` handles business logic, `Repository` handles DB. That separation
  **is** SRP in action.

**✅ Good — each class has one responsibility:**

```java
public class UserRepository {
    public void save(String name, String email) {
        db.save(name, email);
    }
}

public class EmailService {
    public void sendWelcome(String name, String email) {
        emailClient.send(email, "Welcome " + name);
    }
}

public class UserLogger {
    public void logCreated(String name) {
        logger.info("User created: " + name);
    }
}   
```

**❌ Bad — one class doing everything:**

```java
public class UserService {

    public void createUser(String name, String email) {
        // 1. Save to DB
        db.save(name, email);

        // 2. Send welcome email
        emailClient.send(email, "Welcome " + name);

        // 3. Write to log
        logger.info("User created: " + name);
    }
}
```

> **Quick check:** ask "what are the reasons this class might change?" If you can list more than one answer, it's an SRP
> violation.

**Rule of thumb for each Spring Boot layer:**

| Layer             | Responsibility                                                      |
|-------------------|---------------------------------------------------------------------|
| `@RestController` | Only reads request, calls service, returns response. Nothing else.  |
| `@Service`        | Only orchestrates or contains one specific piece of business logic. |
| `@Repository`     | Only talks to the DB. No if-else, no formatting, no external calls. |
| `@Component`      | One focused utility (formatting, validation, encoding, etc.).       |

### 2. Open/Closed Principle (OCP)

- Open for extension, closed for modification.
- Add new features by writing new code — never by editing existing, tested, working code. Use interfaces and
  polymorphism.

**✅ Good — add new type = new class only:**

```java
public interface PaymentGateway {
    void pay(double amount);
}

public class UpiPayment implements PaymentGateway {
    public void pay(double amount) {
        System.out.println("Paid via UPI: " + amount);
    }
}

public class CardPayment implements PaymentGateway {
    public void pay(double amount) {
        System.out.println("Paid via Card: " + amount);
    }
}

// Add PayPal? Just new class.
// Zero changes to existing code.
```

**❌ Bad — add new type = edit old code:**

```java
public class PaymentService {

    public void pay(String type, double amount) {
        if (type.equals("UPI")) {
            System.out.println("Paid via UPI: " + amount);
        } else if (type.equals("CARD")) {
            System.out.println("Paid via Card: " + amount);
        }
        // Add PayPal?
        // You MUST edit this class!
    }
}
```

### 3. Liskov Substitution Principle (LSP)

- Subclasses must be substitutable for their parent class without breaking the program.
- If class `B` extends class `A`, you should be able to use `B` anywhere `A` is used — and nothing should break or
  surprise you.

**✅ Good — honest, independent classes:**

```java
public interface Shape {
    int area();
}

public class Rectangle implements Shape {
    private int width, height;

    public Rectangle(int w, int h) {
        this.width = w;
        this.height = h;
    }

    public int area() {
        return width * height;
    }
}

public class Square implements Shape {
    private int side;

    public Square(int side) {
        this.side = side;
    }

    public int area() {
        return side * side;
    }
}
// Both implement Shape.
// No surprises. No overrides.
```

**❌ Bad — subclass breaks parent's contract:**

```java
public class Rectangle {
    protected int width, height;

    public void setWidth(int w) {
        this.width = w;
    }

    public void setHeight(int h) {
        this.height = h;
    }

    public int area() {
        return width * height;
    }
}

public class Square extends Rectangle {
    // Breaks LSP! Square forces both sides equal — but caller doesn't know that.
    public void setWidth(int w) {
        this.width = w;
        this.height = w; // surprise!
    }
}
```

### 4. Interface Segregation Principle (ISP)

- No class should be forced to implement methods it doesn't need.
- Split fat interfaces into smaller, focused ones. A class should only implement what it actually uses — not carry dead
  weight.

**✅ Good — small focused interfaces:**

```java
public interface Workable {
    void work();
}

public interface Eatable {
    void eat();
}

public interface Sleepable {
    void sleep();
}

// Human implements all three
public class Human implements Workable, Eatable, Sleepable {
    public void work() { /*...*/ }

    public void eat() { /*...*/ }

    public void sleep() { /*...*/ }
}

// Robot only implements what it needs
public class Robot implements Workable {
    public void work() {
        System.out.println("Working...");
    }
}
```

**❌ Bad — fat interface forces junk methods:**

```java
public interface Worker {
    void work();

    void eat();

    void sleep();
}

// Robot doesn't eat or sleep!
// But is FORCED to implement them.
public class Robot implements Worker {
    public void work() {
        System.out.println("Working...");
    }

    public void eat() {
        // meaningless — robots don't eat
    }

    public void sleep() {
        // meaningless — robots don't sleep
    }
}
```

### 5. Dependency Inversion Principle (DIP)

- High-level modules should not depend on low-level modules.
- Both should depend on abstractions.
- **High-level module** → business logic (what your app does)
- **Low-level module** → implementation details (database, APIs, file system, etc.)
- Depend on "what it does", not "how it does it".

DIP says:

- Your business logic should **not** depend directly on concrete implementations.
- Instead, both should depend on interfaces / abstractions.

**❌ Without DIP (Bad Design) — Order system example:**

```java
class MySQLDatabase {
    void save(String data) {
        System.out.println("Saved to MySQL");
    }
}

class OrderService {
    private MySQLDatabase db = new MySQLDatabase();

    void placeOrder() {
        db.save("order data");
    }
}
```

Problems:

- `OrderService` is tightly coupled to `MySQLDatabase`.
- Switching to PostgreSQL? You must change `OrderService`.
- Hard to test (no mocking).

**✅ With DIP (Good Design):**

**Step 1 — Create abstraction:**

```java
interface Database {
    void save(String data);
}
```

**Step 2 — Low-level implements abstraction:**

```java
class MySQLDatabase implements Database {
    public void save(String data) {
        System.out.println("Saved to MySQL");
    }
}
```

**Step 3 — High-level depends on abstraction:**

```java
class OrderService {
    private Database db;

    OrderService(Database db) {
        this.db = db;
    }

    void placeOrder() {
        db.save("order data");
    }
}
```

**Step 4 — Inject dependency:**

```java
class Scratch {
    public static void main(String[] args) {
        Database db = new MySQLDatabase();
        OrderService service = new OrderService(db);
        service.placeOrder();
    }
}

```

## Design Patterns

- At its core, a design pattern is a formalized, reusable solution to a commonly occurring problem in software design.
- It is **not** a library, a framework, or a piece of concrete code that you can copy and paste into your project.
  Instead, think of a design pattern as an architectural blueprint or a conceptual template.
- It describes a structural way to organize your classes, interfaces, and object interactions to make your codebase more
  flexible, maintainable, and scalable.

### 1. The Core Philosophy: "Don't Reinvent the Wheel"

In software engineering, developers repeatedly run into the same architectural challenges. Decades ago, experienced
software engineers noticed these patterns of problems and documented the most elegant ways to solve them.

Rather than figuring out from scratch how to handle complex object creation, how to decouple incompatible interfaces, or
how to manage complex business workflows, you can apply these battle-tested blueprints.

### 2. Why Do We Use Design Patterns?

- **Common Vocabulary:** Instead of spending an hour explaining a complex communication flow between microservices or
  classes, you can tell your teammate, "I used an Observer pattern here" or "Let's build a Facade for this external
  API." Everyone instantly understands the high-level architecture.
- **Code Reusability and Flexibility:** Design patterns help you write code that adheres to SOLID principles (like the
  Single Responsibility and Open/Closed principles), making your code highly adaptable to changing requirements.
- **Easier Refactoring:** It is much easier to modify or scale a system when its components are loosely coupled and
  organized according to proven structural patterns.

### 3. How Design Patterns Are Grouped

In the software industry, classic design patterns are divided into three main categories based on their primary purpose:

| Category       | Purpose                                                                                                                                    | Example                                                                                                                                     |
|----------------|--------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------|
| **Creational** | How objects are created. Abstract the instantiation process, making your system independent of how its objects are created and composed.   | Implementing a Builder to construct complex, multi-field user delegation payloads cleanly without massive constructors.                     |
| **Structural** | How classes and objects are composed. Use inheritance and interfaces to form larger, more powerful structures while keeping them flexible. | Using an Adapter or Facade to hide the complex query mechanism of Trino/Starburst behind a clean internal interface for your ICaps widgets. |
| **Behavioral** | How objects communicate. Focus on the interaction, algorithms, and distribution of responsibilities between objects.                       | Using a Strategy pattern to easily swap different entitlement/access-control validation algorithms at runtime.                              |

## Creational Patterns

### 1. Singleton Pattern

- The primary purpose of the Singleton pattern is to ensure that a class has only one instance and to provide a global
  point of access to that instance.
- In multi-threaded applications, having multiple instances of certain components — such as database connection pools,
  global configuration managers, or cache coordinators — can lead to inconsistent state, memory leaks, and thread
  collision.

**The Classic Plain-Java Implementation (Double-Checked Locking):**

To make a class a true Singleton in Java, we need to:

1. Hide the constructor (make it `private`) so no other class can call `new`.
2. Create a `private static` variable of the same class type to hold the single instance.
3. Provide a `public static` method (usually `getInstance()`) that returns this instance, creating it if it doesn't
   exist yet (lazy initialization).

In a multi-threaded environment, we must ensure that two threads hitting `getInstance()` at the exact same millisecond
do not create two separate instances. The industry standard for doing this efficiently in plain Java is **Double-Checked
Locking**:

```java
public class SystemConfigManager {

    // 1. The volatile keyword is critical!
    // It prevents compiler instruction reordering, ensuring the instance
    // is fully initialized before it's visible to other threads.
    private static volatile SystemConfigManager instance;

    // 2. Private constructor prevents instantiation via 'new'
    private SystemConfigManager() {
    }

    // 3. Public static access point
    public static SystemConfigManager getInstance() {
        // First check (no synchronization overhead if instance already exists)
        if (instance == null) {
            // Synchronize on the class block to ensure thread-safe creation
            synchronized (SystemConfigManager.class) {
                // Second check (ensures a waiting thread doesn't create a duplicate)
                if (instance == null) {
                    instance = new SystemConfigManager();
                }
            }
        }
        return instance;
    }
}
```

**Plain Java Singleton vs. Spring Singleton**

Since you work with Spring Boot daily, you use "Singletons" constantly. However, Spring's Singleton Bean is
fundamentally different from the classic GoF (Gang of Four) Singleton. This is a classic senior engineer interview
topic, and knowing the distinction is crucial:

| Feature             | Classic GoF Singleton                                                               | Spring Singleton Bean Scope                                                                              |
|---------------------|-------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| Scope of Uniqueness | Unique per JVM Classloader                                                          | Unique per Spring `ApplicationContext` (IoC Container)                                                   |
| How It's Enforced   | Private constructor and static class structure                                      | Enforced by the Spring Container. The class itself is a standard public class with a public constructor. |
| Creation Control    | Hardcoded within the class logic                                                    | Delegated to the Spring IoC Container, which manages lifecycle, dependency injection, etc.               |
| Testability         | Difficult to test/mock because of hardcoded static methods and private constructors | Easy to test since you can inject mock beans using Mockito or create separate contexts                   |

> In your Spring Boot applications, when you annotate a service with `@Service` or `@Component`, Spring registers it as
> a singleton bean by default. If you spun up two separate `ApplicationContext` instances in the same JVM, you would get
> two separate instances of that bean — whereas a classic GoF Singleton would remain strictly singular across the entire
> JVM.

### 2. Builder Pattern

- The Builder Pattern is an essential creational pattern that solves a major problem in Java: constructing complex
  objects with many fields, especially when several of those fields are optional.
- Without a Builder, you are stuck with two bad choices:
    1. **Telescoping Constructors:** Writing 5 different overloaded constructors. This becomes a nightmare to read and
       maintain.
    2. **JavaBeans Pattern (no-arg constructor + setters):** This allows the object to be instantiated in an incomplete
       or invalid state before all setters are called, and completely destroys immutability, which is dangerous in
       highly secure multi-threaded banking systems.

**Analogy — ordering a custom burger:**

If the kitchen only allowed "fixed" menu items, they would need a separate recipe and constructor for every single
combination of ingredients:

- Burger with just bun and patty.
- Burger with bun, patty, and cheese.
- Burger with bun, patty, cheese, and lettuce.
- Burger with bun, patty, lettuce, and tomato (but no cheese).

This is incredibly hard to read. Furthermore, if you accidentally swap two boolean parameters (like passing `true` for
lettuce instead of tomato), the compiler won't catch the error, leading to silent bugs.

Instead of pre-assembling every option, the restaurant uses an assembly line. You start with the mandatory base (the bun
and patty), and then you guide the chef step-by-step: "Add cheese. Add lettuce. Hold the tomato." When you are
completely done customizing, the chef wraps it up and hands it to you.

**The Code: How We Do It in Plain Java**

```java
public class Burger {
    // All fields are final because once the burger is served, you can't alter it (immutability)
    private final String bun;       // Required
    private final String patty;     // Required
    private final boolean cheese;   // Optional
    private final boolean lettuce;  // Optional
    private final boolean tomato;   // Optional

    // 1. Private constructor: Forces instantiation exclusively through the Builder
    private Burger(Builder builder) {
        this.bun = builder.bun;
        this.patty = builder.patty;
        this.cheese = builder.cheese;
        this.lettuce = builder.lettuce;
        this.tomato = builder.tomato;
    }

    // Getters only (No setters, keeping the object immutable)
    public String getBun() {
        return bun;
    }

    public String getPatty() {
        return patty;
    }

    public boolean hasCheese() {
        return cheese;
    }

    public boolean hasLettuce() {
        return lettuce;
    }

    public boolean hasTomato() {
        return tomato;
    }

    @Override
    public String toString() {
        return "Burger [Bun=" + bun + ", Patty=" + patty + ", Cheese=" + cheese + ", Lettuce=" + lettuce + ", Tomato=" + tomato + "]";
    }

    // 2. The Static Inner Builder (The assembly line worker)
    public static class Builder {
        private final String bun;   // Required
        private final String patty; // Required

        // Optionals initialized to safe default values
        private boolean cheese = false;
        private boolean lettuce = false;
        private boolean tomato = false;

        // The builder constructor mandates the absolute minimum required fields
        public Builder(String bun, String patty) {
            this.bun = bun;
            this.patty = patty;
        }

        // Fluent "setter" methods that modify the builder and return "this" (the builder itself)
        public Builder addCheese() {
            this.cheese = true;
            return this; // Returning 'this' allows us to chain methods!
        }

        public Builder addLettuce() {
            this.lettuce = true;
            return this;
        }

        public Builder addTomato() {
            this.tomato = true;
            return this;
        }

        // 3. The final "wrap it up" step
        public Burger build() {
            return new Burger(this);
        }
    }
}
```

Now, look how clean, readable, and self-documenting it is to construct different burgers from your main method:

```java
public class Restaurant {
    public static void main(String[] args) {
        // Build a simple cheeseburger
        Burger cheeseburger = new Burger.Builder("Brioche", "Beef")
                .addCheese()
                .build();

        // Build a fully loaded burger (order of optional ingredients doesn't matter!)
        Burger loadedBurger = new Burger.Builder("Sesame", "Chicken")
                .addLettuce()
                .addCheese()
                .addTomato()
                .build();

        System.out.println(cheeseburger);
        System.out.println(loadedBurger);
    }
}
```

**How This Maps to Spring & Lombok**

You will see this design pattern utilized constantly across Spring Boot because it makes writing clean APIs incredibly
easy:

**1. Spring's `ResponseEntity` (HTTP Responses)**

When writing REST controller endpoints, you often need to return an HTTP response with headers, status codes, and a
body. Instead of a messy multi-parameter constructor, Spring provides a builder pattern:

```java

@GetMapping("/api/burger")
public ResponseEntity<Burger> getBurger() {
    Burger burger = new Burger.Builder("Brioche", "Beef").addCheese().build();

    // Spring's built-in ResponseEntity Builder in action:
    return ResponseEntity.ok()                      // Sets status to 200 OK
            .header("Custom-Header", "BurgerTime")   // Custom header config
            .body(burger);                           // Attaches the payload and returns the response
}
```

**2. Lombok's `@Builder`**

In modern Spring Boot development, writing the manual static inner class is considered boilerplate. Lombok gives us a
shortcut. By adding `@Builder` to your model class, Lombok's annotation processor generates the exact same static inner
class and builder methods for you at compile-time:

```java
import lombok.Builder;
import lombok.Getter;

@Getter
@Builder // Lombok automatically writes the entire inner Builder class for you!
public class Burger {
    private final String bun;
    private final String patty;
    private final boolean cheese;
    private final boolean lettuce;
    private final boolean tomato;
}
```

### 3. Factory Method Pattern

- Imagine a smart vending machine that dispenses hot drinks.
- As a customer, you don't want to worry about the internal recipe. You don't want to manually grab coffee beans, grind
  them, heat water to exactly 90°C, and pour the milk.
- If the vending machine forced you to do that, it would be a terrible user experience. Instead, you simply walk up,
  press the "Espresso" or "Latte" button, and the machine handles the complex assembly.
- In your code, you receive a standard cup of "Drink" (a common interface) without ever knowing the exact class or steps
  used to make it.
- In software, the Factory Method Pattern defines an interface for creating an object, but lets the subclasses or
  factory classes decide exactly which class to instantiate.
- It decouples your business logic from the concrete implementation of the objects it needs.

**The Code: How We Do It in Plain Java**

**1. Define the Common Product Interface** — every concrete product must adhere to the same contract:

```java
public interface Drink {
    void prepare();
}
```

**2. Create the Concrete Products** — the actual classes that implement our interface:

```java
public class Espresso implements Drink {
    @Override
    public void prepare() {
        System.out.println("Brewing a strong, concentrated Espresso shot...");
    }
}

public class Latte implements Drink {
    @Override
    public void prepare() {
        System.out.println("Steaming milk and mixing with a shot of Espresso to make a Latte...");
    }
}
```

**3. Create the Factory** — the factory is the "vending machine." It encapsulates the instantiation logic so that the
client code (the person using the vending machine) doesn't have to use the `new` keyword or know about `Espresso` or
`Latte` directly.

```java
public class DrinkFactory {

    // The factory method determines which object to create based on input
    public static Drink getDrink(String drinkType) {
        if (drinkType == null) {
            return null;
        }

        switch (drinkType.toUpperCase()) {
            case "ESPRESSO":
                return new Espresso();
            case "LATTE":
                return new Latte();
            default:
                throw new IllegalArgumentException("Unknown drink type: " + drinkType);
        }
    }
}
```

**4. Using the Factory in the Client Application** — notice how the client code never uses the `new` keyword to create
an `Espresso` or `Latte` object. It only interacts with the abstract `Drink` interface:

```java
public class VendingMachineApplication {
    public static void main(String[] args) {
        // We want an espresso. We don't say "new Espresso()".
        // We let the factory do the heavy lifting.
        Drink customerOrder = DrinkFactory.getDrink("ESPRESSO");
        customerOrder.prepare(); // Prints: Brewing a strong, concentrated Espresso shot...

        // Now we want a latte
        Drink anotherOrder = DrinkFactory.getDrink("LATTE");
        anotherOrder.prepare(); // Prints: Steaming milk...
    }
}
```

**Why is this beneficial?**

If tomorrow you decide to add a new drink, like "Cappuccino", you only need to write the `Cappuccino` class and add one
case to your `DrinkFactory`. Your main application code doesn't change at all because it only expects a `Drink`.

**How This Applies to Spring Boot**

As a Spring Boot engineer, the Factory pattern is the absolute backbone of your entire application:

**1. The IoC Container (`BeanFactory`)**

In Spring, you rarely write `new MyService()`. Instead, you annotate your classes with `@Service` or `@Component` and
let Spring manage them.

The core of Spring's Inversion of Control (IoC) is the `BeanFactory`. The `BeanFactory` is a massive, highly optimized
Factory class. When you request a bean (or when Spring injects one via `@Autowired`), Spring acts as the vending
machine:

```java
// Under the hood, Spring's ApplicationContext acts as a Factory Method:
MyService service = applicationContext.getBean(MyService.class);
```

You don't care how `MyService` was created, what other beans were injected into its constructor, or how its lifecycle is
managed. You just press the button and receive your "bean."

**2. The `@Bean` Annotation**

When you write a configuration class in Spring, you are explicitly creating custom Factory Methods:

```java

@Configuration
public class AppConfig {

    // This method is a Factory Method!
    // Spring executes this method and registers the returned object in its container.
    @Bean
    public Drink customCoffee() {
        return new Espresso();
    }
}
```

**Summary**

- The Factory Method Pattern is about delegating object creation.
- It shields your application from the details of how complex objects are created.
- It reduces tight coupling by returning interfaces instead of concrete classes.
- It serves as the foundation of Spring's Dependency Injection Engine (`BeanFactory`).

### 4. Prototype Pattern

- Imagine you are applying for a visa and have to fill out a massive 20-page application form.
- 18 of those pages are exactly the same for every single application (general terms, country laws, embassy addresses,
  and default disclaimers). Only the last 2 pages contain your specific personal details.
- If you had to write all 20 pages by hand from scratch every single time, it would take hours and waste a massive
  amount of energy.
- Instead, you keep a "master copy" (a template) that is pre-filled with those 18 pages of static information. When you
  need a new application, you simply put the master copy on a photocopy machine to clone it, and then you quickly
  handwrite your specific personal details on the new copy.
- In software, the Prototype Pattern is used when creating a brand-new object from scratch is too "expensive" (e.g., it
  requires heavy database queries, reading configuration files, or complex calculations). Instead of using the `new`
  keyword and rebuilding the object step-by-step, you clone an existing, pre-configured instance and modify only what is
  different.

**The Code: How We Do It in Plain Java**

In Java, we can implement the Prototype Pattern using the built-in `Cloneable` interface and overriding the `clone()`
method.

Example: a customizable `EmailTemplate` class that fetches massive default disclaimer text (simulating an expensive
operation) once, and then clones it.

**1. Implement `Cloneable`** to tell the JVM it's safe to make field-for-field copies of this object:

```java
public class EmailTemplate {
    private String header;
    private String body;
    private String expensiveDisclaimer;

    public EmailTemplate() {
        try {
            // Simulating a heavy resource-intensive initialization
            System.out.println("Connecting to Database to fetch global disclaimer...");
            Thread.sleep(2000); // Sleep for 2 seconds
            this.expensiveDisclaimer = "DISCLAIMER: This email is confidential and property of VendingCorp...";
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
    }

    // Setters and Getters
    public void setHeader(String header) {
        this.header = header;
    }

    public void setBody(String body) {
        this.body = body;
    }

    public String getHeader() {
        return header;
    }

    public String getBody() {
        return body;
    }

    public String getExpensiveDisclaimer() {
        return expensiveDisclaimer;
    }

    // 2. Override the clone() method to perform the copy operation
    @Override
    public EmailTemplate clone() {
        try {
            // super.clone() does a fast bitwise memory copy (shallow copy)
            return (EmailTemplate) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError();
            // Should not happen since we implement Cloneable
        }
    }

    @Override
    public String toString() {
        return "EmailTemplate [\n Header=" + header + ",\n Body=" + body + ",\n Disclaimer=" + expensiveDisclaimer + "\n]";
    }
}
```

**2. How We Use It to Save Performance Cost** — instead of calling `new EmailTemplate()` multiple times (which would hit
the "database" over and over), we instantiate a single prototype master object once and clone it dynamically:

```java
// Prototype design pattern
class Scratch {
    public static void main(String[] args) {
        System.out.println("--- Creating the Master Prototype ---");

        EmailTemplate masterPrototype = new EmailTemplate();

        // Hits database once
        masterPrototype.setHeader("Welcome to VendingCorp!");
        System.out.println("--- Cloning for Customer A ---");

        // We clone the master template. This is instant! No database latency.
        EmailTemplate customerAEmail = masterPrototype.clone();
        customerAEmail.setBody("Hello Customer A, your order is ready.");
        System.out.println("--- Cloning for Customer B ---");

        EmailTemplate customerBEmail = masterPrototype.clone();
        customerBEmail.setBody("Hello Customer B, your invoice is attached.");

        System.out.println(customerAEmail);
        System.out.println(customerBEmail);
    }
}
```

**How This Applies to Spring Boot: The Prototype Bean Scope**

- In Spring, when you define a class with `@Component` or `@Service`, Spring registers it as a Singleton by default —
  meaning only one instance of that bean lives inside the container.
- However, sometimes you need a stateful bean where every class that injects it gets a fresh, independent instance. For
  this, you use Prototype Scope:

```java

@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE) // Or simply @Scope("prototype")
public class UserSessionTracker {
    private String currentActiveUser;
    // State is local to whoever requested this bean!
}
```

**The Difference under the hood:**

- **Singleton Scope:** When class `A` and class `B` both `@Autowired` a singleton bean, they are handed the exact same
  shared memory reference from Spring's IoC container.
- **Prototype Scope:** When class `A` and class `B` `@Autowired` a prototype bean, Spring's container acts as a
  prototype factory — it spins up and configures a brand-new instance for each of them, ensuring they never share or
  corrupt each other's local state.

## Structural Patterns

### What are Structural Patterns?

- If Creational patterns are about **how you construct individual objects**, Structural patterns are about **how you
  connect those objects together** to form larger, flexible structures.
- They ensure that when different parts of a system need to work together, they do so cleanly without tightly coupling
  your code.

### 1. The Adapter Pattern

- **Layman Analogy: The Travel Power Adapter**

    - Imagine you travel to Europe with a US laptop charger. Your charger has a 3-prong US plug, but the hotel wall
      socket
      only accepts 2-prong European plugs.
    - You don't buy a brand-new laptop, nor do you rewire the hotel wall. Instead, you use a **travel power adapter**.
    - The adapter sits in the middle: it accepts your US plug on one side and fits into the European socket on the
      other.
    - In software, the **Adapter Pattern** bridges two incompatible interfaces so they can communicate without modifying
      their original source code.


- **The Code: How We Do It in Plain Java**

Suppose your application relies on a standard interface for processing payments:

```java
// The Target interface your application expects
public interface PaymentProcessor {
    void processPayment(double amountInDollars);
}

```

Now, you need to integrate a third-party library (`FancyStripeSDK`), but its methods and parameters are completely
different:

```java
// The Adaptee: A third-party class with an incompatible interface
public class FancyStripeSDK {
    public void makeTransaction(double amountInCents, String currency) {
        System.out.println("Charged $" + (amountInCents / 100.0) + " via FancyStripeSDK (" + currency + ")");
    }
}

```

Instead of changing your existing codebase or modifying the third-party library, you write an **Adapter**:

```java
// The Adapter translates calls from PaymentProcessor into calls to FancyStripeSDK
public class StripePaymentAdapter implements PaymentProcessor {
    private final FancyStripeSDK stripeSDK;

    public StripePaymentAdapter(FancyStripeSDK stripeSDK) {
        this.stripeSDK = stripeSDK;
    }

    @Override
    public void processPayment(double amountInDollars) {
        // Convert dollars to cents as expected by the third-party library
        double amountInCents = amountInDollars * 100;
        stripeSDK.makeTransaction(amountInCents, "USD");
    }
}

```

Now, your main application code uses the adapter transparently:

```java
public class AdapterDemo {
    public static void main(String[] args) {
        FancyStripeSDK externalSdk = new FancyStripeSDK();

        // Wrap the incompatible SDK in our adapter
        PaymentProcessor processor = new StripePaymentAdapter(externalSdk);

        // Your app calls the familiar method signature cleanly
        processor.processPayment(49.99);
    }
}
```

- **How This Applies to Spring Boot**

Spring Boot uses the Adapter pattern extensively under the hood to keep your code decoupled from internal framework
requirements:

1. **Spring MVC** **HandlerAdapter**: Spring MVC can handle web requests using annotated `@Controller` methods,
   functional endpoints, or legacy servlet handlers. To execute them uniformly, Spring uses implementations of
   `HandlerAdapter` (like `RequestMappingHandlerAdapter`) to adapt HTTP requests to whichever method signature you wrote
   in your controller.
2. **Spring Security**: Spring Security uses adapters (such as custom `UserDetailsService` implementations) to adapt
   your domain `User` entity or external LDAP user format into Spring Security's expected `UserDetails` interface.

### 2. The Facade Pattern

#### 1. Layman Analogy: The Hotel Concierge

- Imagine staying at a luxury hotel. You want to plan a night out: you need to book a restaurant table, reserve theater
  tickets, and hire a private taxi.
- Option A without a concierge: You have to call the restaurant manager yourself, call the theater box office, and call
  the taxi company. You manage three separate conversations, handle three different confirmation formats, and deal with
  all the complexity.
- Option B with a **Hotel Concierge**: You make **one single phone call** to the concierge desks and say, *"I want
  dinner at 7, theater at 8:30, and a cab at 10."* The concierge handles all the underlying calls, coordinating between
  the three separate services behind the scenes.
- In software, a **Facade Pattern** provides a simple, unified interface in front of a complex set of subsystem classes.

#### 2. The Code: How We Do It in Plain Java

Imagine a e-commerce checkout process. Placing an order requires interacting with four separate systems: inventory,
payment, shipping, and email notifications.

##### Subsystem Classes (The complex machinery behind the scenes):

```java
public class InventoryService {
    public boolean checkStock(String productId) {
        System.out.println("Checking stock for product: " + productId);
        return true;
    }
}

public class PaymentService {
    public boolean processPayment(String userId, double amount) {
        System.out.println("Processing payment of $" + amount + " for user: " + userId);
        return true;
    }
}

public class ShippingService {
    public void scheduleDelivery(String productId, String address) {
        System.out.println("Scheduling delivery for " + productId + " to " + address);
    }
}

public class EmailService {
    public void sendConfirmation(String userId) {
        System.out.println("Sending order confirmation email to user: " + userId);
    }
}

```

##### The Facade (The "Concierge"):

Instead of making the controller or client deal with all 4 services, we wrap them in an `OrderFacade`:

```java
public class OrderFacade {
    private final InventoryService inventoryService;
    private final PaymentService paymentService;
    private final ShippingService shippingService;
    private final EmailService emailService;

    public OrderFacade() {
        this.inventoryService = new InventoryService();
        this.paymentService = new PaymentService();
        this.shippingService = new ShippingService();
        this.emailService = new EmailService();
    }

    // A single, clean method that orchestrates the entire workflow
    public boolean placeOrder(String productId, String userId, double amount, String address) {
        System.out.println("--- Starting Order Checkout Flow ---");

        if (!inventoryService.checkStock(productId)) {
            return false;
        }

        if (!paymentService.processPayment(userId, amount)) {
            return false;
        }

        shippingService.scheduleDelivery(productId, address);
        emailService.sendConfirmation(userId);

        System.out.println("--- Order Successfully Placed! ---\n");
        return true;
    }
}

```

##### Using the Facade:

The client code stays completely clean and only calls one method:

```java
public class ECommerceApplication {
    public static void main(String[] args) {
        // One facade object handles the complex orchestration
        OrderFacade orderFacade = new OrderFacade();

        // Single method call replaces 4 separate service interactions
        orderFacade.placeOrder("PROD-101", "USER-555", 99.99, "123 Main St");
    }
}
```

#### 3. How This Applies to Spring Boot

You write Facades constantly in Spring Boot without even realizing it!

1. **Service Layer Orchestration**: In a typical Spring Boot REST API, your `@RestController` shouldn't be calling 5
   different repositories, notification classes, and external APIs directly. Instead, you create an orchestration
   service annotated with `@Service` (e.g., `OrderOrchestrationService`) that acts as a Facade.
2. **API Gateways in Microservices**: In microservice architectures, **Spring Cloud Gateway** acts as a giant Facade for
   the entire backend system. Front-end clients send a single request to the Gateway, and the Gateway routes,
   aggregates, and transforms requests across dozens of underlying microservices.

### Summary

The **Facade Pattern**:

1. Hides the complexity of a multi-step subsystem behind a single, clean method interface.
2. Promotes **loose coupling** between your client application and underlying services.

```
WITHOUT FACADE (High Coupling &amp; Complexity):
┌────────┐
│        │ ───────> [ InventoryService ]
│        │ ───────> [ PaymentService   ]
│ Client │ ───────> [ ShippingService  ]
│        │ ───────> [ EmailService     ]
└────────┘

WITH FACADE (Clean, Single Point of Interaction):
┌────────┐          ┌─────────────┐ 
│        │          │             │ ───────> [ InventoryService ]
│        │ ───────> │             │ ───────> [ PaymentService   ]
│ Client │          │ OrderFacade │ ───────> [ ShippingService  ]
└────────┘          │             │ ───────> [ EmailService     ]
                    └─────────────┘

```

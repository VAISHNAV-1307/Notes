# Chapter 3: Spring Data JPA

## 3.1 JPA (Java Persistence API)

- JPA is a Java **specification** — a set of interfaces and rules — that defines how to map Java objects (entities) to database tables, and how to manage them (CRUD operations, queries, transactions).
- It is only a specification, not an implementation — much like an interface in Java, it defines *what* needs to be done, but not *how*.
- Historically, developers used JDBC directly, writing large amounts of SQL by hand. To simplify this, ORM frameworks like Hibernate were created, and JPA was later introduced as a standard API for ORM in Java.

**Common JPA implementations:**
- Hibernate
- EclipseLink
- OpenJPA

Hibernate is the most popular JPA implementation, and Spring Boot uses it by default under the hood.

**JPA provides:**
- Mapping of Java classes to DB tables (via annotations like `@Entity`, `@Table`)
- Database CRUD operations without writing SQL directly
- Management of relationships (`@OneToMany`, `@ManyToOne`, etc.)
- Querying using JPQL (Java Persistence Query Language)
- Transaction management via `EntityManager`

**Core JPA annotations:**

| Annotation | Purpose |
|---|---|
| `@Entity` | Marks a class as a JPA entity (maps to a table) |
| `@Table` | Maps to a specific table name (optional if the table name matches the class name) |
| `@Id` | Marks the primary key field |
| `@GeneratedValue` | Auto-generates the primary key (strategy options: `AUTO`, `IDENTITY`, `SEQUENCE`) |
| `@Column` | Maps a field to a specific column (optional if the names already match) |
| `@OneToOne`, `@OneToMany`, `@ManyToOne`, `@ManyToMany` | Relationship mappings |

## 3.2 Hibernate

Hibernate is a Java-based ORM (Object-Relational Mapping) framework. It implements the JPA specification and adds extra features to seamlessly map Java objects (entities) to relational database tables.

In simple terms, Hibernate automates the "old" JDBC workflow — managing connections, building SQL queries, handling result sets, and mapping data to objects.

**Core Hibernate concepts:**

| Concept | Explanation |
|---|---|
| `SessionFactory` | A heavyweight object, created once at application startup, that manages database connections |
| `Session` | Represents a single unit of work with the database (a wrapper around a JDBC connection) |
| `Transaction` | Manages commit and rollback operations within a session |
| `Entity` | A Java class mapped to a database table |

**Advantages of Hibernate:**
- Simplifies database operations (no direct JDBC boilerplate)
- Automatic table creation (if configured)
- Database independence (you can switch databases easily)
- Powerful caching (first- and second-level cache)
- Manages relationships and cascades automatically

**Example — Hibernate without Spring:**

```java
Session session = sessionFactory.openSession();
Transaction tx = session.beginTransaction();

Student student = new Student();
student.setName("Vaishnav");
student.setEmail("test@gmail.com");

session.save(student);
tx.commit();
session.close();
```

## 3.3 EntityManager

`EntityManager` is the main interface in JPA for interacting with the persistence context — it's your gateway to the database when using JPA. It manages saving, updating, deleting, and querying entities.

**Key responsibilities of `EntityManager`:**
- Persisting new entities (`persist`)
- Finding entities by primary key (`find`)
- Updating entities (automatically, once managed)
- Removing entities (`remove`)
- Executing queries (JPQL or native SQL)
- Managing the persistence context

**Core methods:**

| Method | Purpose |
|---|---|
| `persist(entity)` | Inserts a new entity into the database |
| `find(entityClass, primaryKey)` | Finds an entity by primary key |
| `merge(entity)` | Updates an existing entity, or saves it if detached |
| `remove(entity)` | Deletes an entity |
| `createQuery()` | Creates a JPQL query |
| `createNativeQuery()` | Creates a native SQL query |
| `flush()` | Synchronizes the persistence context with the database |
| `clear()` | Clears the persistence context (detaches all entities) |
| `close()` | Closes the `EntityManager` |

> **Note:** `flush()` forces synchronization with the database before the transaction commits.

**Entity lifecycle with `EntityManager`:**

- **Transient** – A new object, not associated with an `EntityManager`.
- **Persistent** – Managed by the `EntityManager` (after `persist()` or `find()`).
- **Detached** – Previously persistent, now no longer managed (`EntityManager` closed or cleared).
- **Removed** – Marked for deletion via `remove()`.

```java
EntityManagerFactory emf = Persistence.createEntityManagerFactory("myPU");
EntityManager em = emf.createEntityManager();

em.getTransaction().begin();

Student student = new Student();
student.setName("Vaishnav");
student.setEmail("test@gmail.com");

em.persist(student); // inserts into DB

Student s = em.find(Student.class, 1L); // retrieves by primary key

em.getTransaction().commit();
em.close();
```

## 3.4 Persistence Context

The persistence context is a set of managed entity instances in which, for any given persistent entity identity, there is exactly one unique entity instance.

In simple terms, it's like a cache — or a memory area — managed by the `EntityManager`. When you fetch an entity, it's stored in the persistence context, and any changes to it are tracked automatically until the transaction commits.

**Key facts:**
- Each entity is unique per database identity (primary key).
- It's managed by the `EntityManager`.
- Changes to entities are tracked automatically.
- It functions as a first-level cache, maintained by the `EntityManager`, for entities within a transaction or session.

**Persistence Context = First-level cache + identity manager + change tracker**

**Why the persistence context matters:**
- **Identity guarantee** — the same entity is never loaded twice within the context.
- **Automatic change tracking** — updates are flushed to the database at transaction commit.
- **Fewer DB calls** — fetched entities are kept in memory.
- **Transactional write-behind** — updates happen at commit time, not immediately (unless flushed manually).

```java
em.getTransaction().begin();

Student s1 = em.find(Student.class, 1L); // fetches from DB, stores in persistence context
Student s2 = em.find(Student.class, 1L); // returned from persistence context, no DB hit

s1.setName("Vaishnav Updated"); // change is tracked automatically

em.getTransaction().commit(); // flushes changes to DB

em.close(); // clears the persistence context
```

Here: the first `find()` hits the database and stores `Student(1L)` in the context; the second `find()` returns the cached instance from the context; updating `s1` is tracked automatically; on commit, changes are flushed to the database; and `close()` clears the context.

### 3.4.1 States of Entities in the Persistence Context

| State | Explanation |
|---|---|
| Transient | A new object, not associated with any persistence context (e.g., `new Student()`) |
| Persistent | Managed by the `EntityManager` and persistence context (`em.persist()`, `em.find()`) |
| Detached | Was persistent, but no longer associated (after `em.close()` or outside a transaction) |
| Removed | Marked for deletion (`em.remove()`); will be deleted on flush/commit |

### 3.4.2 Persistence Context Scope

**Types:**

1. **Transaction-scoped** (the JPA default) — exists only within a transaction. Starts with `em.getTransaction().begin()` and ends with a commit or rollback.
2. **Extended-scoped** (used with stateful EJBs) — exists beyond a single transaction. Useful for long-running conversations in an application (less common in Spring).

### 3.4.3 Persistence Context vs. Cache

| Aspect | Persistence Context | Cache (2nd Level) |
|---|---|---|
| Scope | Per `EntityManager` / transaction | Application-wide (`SessionFactory`) |
| Level | First-level (mandatory) | Second-level (optional) |
| Usage | Ensures consistency within a transaction | Reduces DB calls across transactions |
| Implementation | JPA specification | Hibernate-specific (Ehcache, Redis, etc.) |

### 3.4.4 Basic CRUD Operations via `EntityManager`

| Operation | Method | Notes |
|---|---|---|
| Create | `persist(entity)` | Adds a new entity to the database |
| Read | `find(entityClass, primaryKey)` | Fetches an entity by ID |
| Update | Automatic for managed entities; `merge(entity)` for detached ones | Changes are tracked automatically |
| Delete | `remove(entity)` | Deletes an entity from the database |

## 3.5 Spring Data JPA

Spring Data JPA is part of the Spring Data project, and it simplifies the implementation of data access layers using JPA. It's a library built on top of JPA and Hibernate that reduces the boilerplate needed for database operations.

**Before Spring Data JPA**, using plain JPA involved:
- Writing a DAO interface
- Writing its implementation class
- Injecting `EntityManager`
- Implementing CRUD methods manually

**Spring Data JPA removes this hassle by:**
- Providing ready-made repository interfaces with built-in CRUD, paging, and sorting methods
- Allowing automatic query generation from method names (e.g., `findByName`)
- Supporting custom queries easily, via `@Query`
- Integrating seamlessly with Spring Boot for auto-configuration

**Core features of Spring Data JPA:**

- **Repository abstraction** — use interfaces like `CrudRepository` or `JpaRepository`, without writing any implementation code.
- **Derived queries** — write a method like `findByEmail`, and Spring Data JPA generates the SQL behind the scenes.
- **Custom queries with `@Query`** — define JPQL or native queries for more complex scenarios.
- **Paging and sorting** — built-in support for efficiently paginating and sorting results.
- **Specifications** — build dynamic queries with the Specification API.

### 3.5.1 Configuring `application.properties` for Spring Data JPA

```properties
# ==============================
# Database Configuration
# ==============================
spring.datasource.url=jdbc:mysql://localhost:3306/your_db_name
spring.datasource.username=root
spring.datasource.password=your_password
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver

# ==============================
# JPA & Hibernate Configuration
# ==============================
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

# Optional: specify dialect explicitly
spring.jpa.database-platform=org.hibernate.dialect.MySQL8Dialect
```

**Explanation:**

| Property | Purpose |
|---|---|
| `spring.datasource.url` | Database connection URL |
| `spring.datasource.username` / `password` | Database credentials |
| `spring.datasource.driver-class-name` | JDBC driver class |
| `spring.jpa.hibernate.ddl-auto` | Schema generation strategy (`none`, `update`, `create`, `create-drop`, `validate`) |
| `spring.jpa.show-sql` | Prints SQL queries to the console, for debugging |
| `spring.jpa.properties.hibernate.format_sql` | Pretty-prints SQL |
| `spring.jpa.database-platform` | Specifies the Hibernate dialect (optional — auto-detected if omitted) |

**`ddl-auto` options:**

| Option | Behavior |
|---|---|
| `none` | No schema management |
| `update` | Updates the existing schema without dropping data (common in development) |
| `create` | Creates the schema on every startup (drops it if it already exists) |
| `create-drop` | Creates the schema at startup, drops it at shutdown |
| `validate` | Validates the schema against the entities (throws an error on mismatch) |

### 3.5.2 Repository Abstraction

Spring Data JPA provides ready-made interfaces for CRUD operations, eliminating the need to write boilerplate DAO implementations manually.

**1. `CrudRepository`**

A generic Spring Data interface providing CRUD (Create, Read, Update, Delete) operations for an entity.

- Part of the `org.springframework.data.repository` package.
- Uses generics to work with any entity type.
- Extended by `JpaRepository` and other repository types.

```java
public interface CrudRepository<T, ID> extends Repository<T, ID> {
    <S extends T> S save(S entity);
    Optional<T> findById(ID id);
    boolean existsById(ID id);
    Iterable<T> findAll();
    Iterable<T> findAllById(Iterable<ID> ids);
    long count();
    void deleteById(ID id);
    void delete(T entity);
    void deleteAll(Iterable<? extends T> entities);
    void deleteAll();
}
```

Here, `T` is the entity type and `ID` is the type of the primary key.

**2. `PagingAndSortingRepository`**

Extends `CrudRepository`, adding methods for pagination and sorting. Useful when you want to retrieve large numbers of records efficiently:

- **Pagination** — fetch data in pages (e.g., page 0 with 10 records, page 1 with the next 10).
- **Sorting** — retrieve data sorted by specific fields (e.g., name ascending, date descending).

```java
public interface PagingAndSortingRepository<T, ID> extends CrudRepository<T, ID> {
    Iterable<T> findAll(Sort sort);
    Page<T> findAll(Pageable pageable);
}
```

Here, `findAll(Sort sort)` returns all entities sorted by the given criteria, and `findAll(Pageable pageable)` returns entities in paginated form (a `Page` object).

**`Pageable` and `Page`:**

| Term | Explanation |
|---|---|
| `Pageable` | Interface describing pagination information (page number, size, sort). Implemented by `PageRequest` |
| `Page<T>` | A single page of results, including content, total elements, total pages, current page info, etc. |

```java
@Service
public class StudentService {

    @Autowired
    private StudentRepository studentRepository;

    public Iterable<Student> getAllStudentsSorted() {
        return studentRepository.findAll(Sort.by("name").ascending());
    }

    public Page<Student> getStudentsPaginated(int pageNo, int pageSize) {
        Pageable pageable = PageRequest.of(pageNo, pageSize);
        return studentRepository.findAll(pageable);
    }
}
```

**3. `JpaRepository`**

Extends `PagingAndSortingRepository`, adding further JPA-specific methods.

**Hierarchy:**

```
JpaRepository
      ↑
PagingAndSortingRepository
      ↑
CrudRepository
      ↑
Repository
```

`JpaRepository` inherits CRUD, paging, and sorting, and adds extra JPA-specific features for better productivity:

| Method | Purpose |
|---|---|
| `saveAll(Iterable<S> entities)` | Saves multiple entities in a batch |
| `flush()` | Flushes changes in the persistence context to the DB |
| `saveAndFlush(entity)` | Saves an entity and immediately flushes changes |
| `deleteInBatch(Iterable<T> entities)` | Deletes multiple entities in a batch |
| `deleteAllInBatch()` | Deletes all entities in a batch |
| `getOne(ID id)` | Returns a reference (proxy) to the entity without hitting the DB immediately |

```java
public interface JpaRepository<T, ID> extends PagingAndSortingRepository<T, ID> {
    List<T> findAll();
    List<T> findAll(Sort sort);
    List<T> findAllById(Iterable<ID> ids);
    <S extends T> List<S> saveAll(Iterable<S> entities);
    void flush();
    <S extends T> S saveAndFlush(S entity);
    void deleteInBatch(Iterable<T> entities);
    void deleteAllInBatch();
    T getOne(ID id);
}
```

**Important points:**
- `getOne(id)` returns a lazy-loaded proxy; accessing its properties triggers a DB hit.
- `findById(id)` retrieves the entity from the DB immediately.
- Use `saveAll()` and `deleteInBatch()` for better performance in bulk operations.
- `flush()` writes pending changes from the persistence context to the DB, without committing the transaction.

`JpaRepository` is the most powerful repository interface, combining CRUD operations, paging and sorting, and additional JPA-specific methods for batch processing and flushing.

**Comparison:**

| Interface | Features |
|---|---|
| `CrudRepository` | Basic CRUD operations |
| `PagingAndSortingRepository` | CRUD + paging + sorting |
| `JpaRepository` | CRUD + paging + sorting + JPA-specific methods (batch operations, flush, `saveAndFlush`, `getOne`) |

**When to use each:**

1. **`CrudRepository`** — when you only need basic CRUD, with no need for pagination or sorting (e.g., a small admin configuration table). Avoid it if you plan to add pagination or JPA-specific operations later, since you'd need to change the interface you extend.
2. **`PagingAndSortingRepository`** — when you need CRUD plus pagination and sorting, but no JPA-specific batch operations (e.g., listing records with a page number, sorted by a field like a student's name). Avoid it if you need `saveAll`, `flush`, or similar JPA-specific enhancements.
3. **`JpaRepository`** — when you need full CRUD, paging, sorting, plus JPA-specific methods. Suitable for most real-world Spring Boot applications. **Best practice:** always extend `JpaRepository` unless you have a very minimal, CRUD-only use case, since it already includes all the features of the other two.

## 3.6 Derived Query Methods

Spring Data JPA lets you define queries simply by naming methods correctly in your repository interface — no SQL, JPQL, or annotations required. Spring reads the method name, interprets it, and auto-generates the SQL/JPQL behind the scenes.

**Syntax rule:** `findBy<PropertyName><Operation>`

You can also combine logical operators, sorting, nested properties, and more.

```java
@Entity
public class Student {
    @Id
    private Long id;
    private String name;
    private String email;
    private int age;
    private boolean active;
}
```

**Basic derived queries:**

| Method Name | Auto-Generated Query |
|---|---|
| `findByName(String name)` | `SELECT s FROM Student s WHERE s.name = ?1` |
| `findByEmail(String email)` | `SELECT s FROM Student s WHERE s.email = ?1` |
| `findByAge(int age)` | `SELECT s FROM Student s WHERE s.age = ?1` |

**More advanced derived queries:**

| Method Name | What It Does |
|---|---|
| `findByNameAndAge(String name, int age)` | `WHERE name = ? AND age = ?` |
| `findByNameOrEmail(String name, String email)` | `WHERE name = ? OR email = ?` |
| `findByAgeBetween(int start, int end)` | `WHERE age BETWEEN ? AND ?` |
| `findByAgeLessThan(int age)` | `WHERE age < ?` |
| `findByNameLike(String name)` | `WHERE name LIKE ?` |
| `findByEmailContaining(String keyword)` | `WHERE email LIKE %?%` |
| `findByActiveTrue()` | `WHERE active = true` |
| `findByAgeIn(List<Integer> ages)` | `WHERE age IN (?, ?, ...)` |

> **Note:** Use the `@Query` annotation for more complex queries or joins.

### 3.6.1 Query-Derivation Keywords

Spring Data JPA reserves a set of keywords that tell Spring how to generate a query from a method name.

**Common action prefixes:**

| Keyword | Description |
|---|---|
| `findBy` | The most common — retrieves entities (returns a `List` or `Optional` by default) |
| `readBy` | Synonym for `findBy` |
| `getBy` | Synonym for `findBy`, more expressive |
| `queryBy` | Another alias for `findBy` |
| `searchBy` | Alias (not always recommended, and not well documented) |
| `countBy` | Returns a `long` — counts rows matching the condition |
| `existsBy` | Returns a `boolean` — checks for the existence of matching rows |
| `deleteBy` | Deletes records matching the criteria (returns the count of deleted rows) |
| `removeBy` | Synonym for `deleteBy` |

**Condition/operator suffixes:**

| Keyword | Description |
|---|---|
| `And`, `Or` | Logical operators |
| `Between`, `LessThan`, `GreaterThan`, `After`, `Before` | Range or comparison operators |
| `IsNull`, `IsNotNull` | Null checks |
| `Like`, `NotLike` | Pattern matching (with `%`) |
| `Containing`, `StartingWith`, `EndingWith` | Convenience `LIKE` queries |
| `In`, `NotIn` | Collection-based matching |
| `True`, `False` | For boolean fields |
| `IgnoreCase` | Case-insensitive matching |

**Combining prefixes and suffixes:**

```java
findByEmailAndActiveTrue()
countByAgeGreaterThan(int age)
deleteByCreatedDateBefore(LocalDate date)
existsByUsernameIgnoreCase(String username)
findTop3ByOrderByAgeDesc()
```

> **Notes:**
> - Don't mix too many conditions into one method — consider `@Query` or the Specification API instead.
> - Use `Optional<T>` for single-record queries, to avoid manual null handling.

### 3.6.2 `Top` / `First` and `Distinct`

Spring Data JPA lets you limit the number of results returned from a derived query using:

- **`Top`** — get the top N results.
- **`First`** — get the first result, optionally sorted.

These help refine your result set — either by removing duplicates (`Distinct`) or by limiting how many records come back (`Top`/`First`).

**`Distinct`** ensures the query returns only unique results, just like SQL's `DISTINCT` keyword. Spring Data JPA lets you prefix your method name with `distinct` to enable this.

## 3.7 Custom Queries with `@Query`

Derived queries are great, but sometimes you need more: complex logic, joins, grouping, projections, or sorting/filtering beyond what a method name can express. That's when JPQL (Java Persistence Query Language), via `@Query`, comes in handy.

**JPQL:**
- Is an object-oriented query language.
- Works with entities, not tables.
- Uses Java class and field names, not SQL table/column names.

**Syntax:**

```java
@Query("SELECT e FROM EntityName e WHERE e.field = ?1")
ReturnType methodName(ParameterType param);
```

You can use `?1`, `?2`, etc. for positional parameters, or `:paramName` for named parameters (named parameters are used most of the time).

**Native SQL:** works the same way as JPQL, except native SQL uses table names directly, while JPQL uses the entity itself. You need to add `nativeQuery = true` to the `@Query` annotation.

## 3.8 The `@Modifying` Annotation

- Spring Data JPA repositories are **read-only** by default.
- To perform write operations (`UPDATE`, `DELETE`, or `INSERT`) with a custom `@Query`, you must annotate it with `@Modifying` — otherwise, you'll get an error.
- `@Modifying` bypasses the persistence context, which is important to understand.
- In JPA, the persistence context (the first-level cache) tracks managed entities via the `EntityManager`. Changes made to these managed entities are automatically synchronized with the database at commit time. But a JPQL/native `UPDATE`/`DELETE` run via `@Modifying` hits the database **directly**, and does **not** update any entities currently held in memory.
- This can leave you with stale data in memory if you:
  1. Fetched some entities earlier,
  2. Then ran an update using `@Modifying`,
  3. And kept using those same (now stale) entity instances afterward.

**Ways to avoid the stale-memory problem:**

| Approach | Explanation |
|---|---|
| `clearAutomatically = true` | Automatically clears the persistence context after the query runs |
| Manually call `entityManager.clear()` | Do it yourself after the `@Modifying` query |
| Avoid mixing `@Modifying` with managed entities | If you're working with entity instances, prefer changing them directly and letting JPA manage the update |

```java
@Modifying(clearAutomatically = true)
@Transactional
@Query("UPDATE Student s SET s.active = false WHERE s.age > :age")
int deactivateOldStudents(@Param("age") int age);
```

Here, `clearAutomatically = true` ensures the persistence context is cleared automatically, so any subsequent queries reload fresh data.

## 3.9 Relationship Mapping in JPA

In real-world applications, your data isn't isolated — entities relate to one another. JPA helps you map and manage these relationships with just a few annotations.

| Relationship | Annotation |
|---|---|
| One-to-One | `@OneToOne` |
| One-to-Many | `@OneToMany` |
| Many-to-One | `@ManyToOne` |
| Many-to-Many | `@ManyToMany` |

### 3.9.1 One-to-One Relationship

A one-to-one relationship is when one entity is associated with exactly one other entity, and vice versa.

**Examples:**

| Entity A | Entity B |
|---|---|
| User | UserProfile |
| Employee | IDCard |
| Customer | Address |

**Unidirectional `@OneToOne` with a foreign key** (say, each `User` has one `Profile`):

```java
@Entity
public class User {
    @Id
    private Long id;
    private String username;

    @OneToOne(cascade = CascadeType.ALL)
    @JoinColumn(name = "profile_id") // FK column
    private Profile profile;
}

@Entity
public class Profile {
    @Id
    private Long id;
    private String bio;
}
```

Here, `Profile` can only be accessed via `User`.

**Bidirectional `@OneToOne`** (if we also want `Profile` to access `User`):

```java
@Entity
public class Profile {
    @Id
    private Long id;

    private String bio;

    @OneToOne(mappedBy = "profile") // inverse side
    private User user;
}
```

Now `User` owns the relationship, and `Profile` is the inverse side, with `mappedBy = "profile"` referring to the field in `User`.

| Side | Annotation | Notes |
|---|---|---|
| Owning side | `@JoinColumn` | Controls the foreign key |
| Inverse side | `mappedBy` | Refers to the field on the owning side |

By default, `@OneToOne` is **EAGER**, so the `profile` is always loaded along with the `user`.

### 3.9.2 One-to-Many Relationship

A one-to-many relationship means one entity relates to many instances of another entity.

**Examples:**

| One (Parent) | Many (Children) |
|---|---|
| Department | Students |
| BlogPost | Comments |
| Customer | Orders |

**Bidirectional `@OneToMany`** (say, one `Department` has many `Student`s):

```java
// Student entity (owning side)
@Entity
public class Student {
    @Id
    private Long id;
    private String name;

    @ManyToOne
    @JoinColumn(name = "department_id")  // FK in the Student table
    private Department department;
}

// Department entity (inverse side)
@Entity
public class Department {
    @Id
    private Long id;
    private String name;

    @OneToMany(mappedBy = "department", cascade = CascadeType.ALL)
    private List<Student> students = new ArrayList<>();
}
```

Here, `Student` holds the foreign key, so it's the owning side. `Department.students` is the inverse side, using `mappedBy = "department"`. `cascade = CascadeType.ALL` means students will be saved/removed along with their department.

- The default fetch type is **LAZY**.
- In a `@OneToMany` mapping, the owning side is always the parent side.
- It defines a parent-to-child relationship.
- Avoid `CascadeType.ALL` unless you're fully confident it's the right behavior.

### 3.9.3 Many-to-One Relationship

A many-to-one relationship means many child entities relate to one parent entity — it's the reverse of `@OneToMany`.

**Examples:**

| Many (Child) | One (Parent) |
|---|---|
| Students | Department |
| Orders | Customer |
| Comments | BlogPost |

Say each `Student` belongs to one `Department`:

```java
@Entity
public class Student {
    @Id
    private Long id;

    private String name;

    @ManyToOne
    @JoinColumn(name = "department_id") // FK column in the Student table
    private Department department;
}
```

Here, `@ManyToOne` marks the child (owning) side, and `@JoinColumn` creates the foreign key in the child table (`department_id` in `Student`). There's no need for `mappedBy` — it's only needed on the inverse side.

```java
@Entity
public class Department {
    @Id
    private Long id;

    private String name;

    @OneToMany(mappedBy = "department")
    private List<Student> students = new ArrayList<>();
}
```

Here, `mappedBy = "department"` points to the field in the `Student` entity — this is the inverse side.

- The default fetch type is **EAGER**.
- Cascading is generally not used here, unless you're always creating the parent together with the child.
- In a `@ManyToOne` mapping, the owning side is always the child side.
- It defines a child-to-parent mapping — the child owns the relationship because the foreign key lives in the child's table.

### 3.9.4 Many-to-Many Relationship

A many-to-many relationship means many entities on one side relate to many entities on the other side.

**Examples:**

| Entity A | Entity B |
|---|---|
| Student | Course |
| Author | Book |
| User | Role |

For example: a student can enroll in many courses, and each course can have many students.

```java
@Entity
public class Student {
    @Id
    private Long id;
    private String name;

    @ManyToMany
    @JoinTable(
        name = "student_course",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id")
    )
    private List<Course> courses = new ArrayList<>();
}

@Entity
public class Course {
    @Id
    private Long id;
    private String title;

    @ManyToMany(mappedBy = "courses")
    private List<Student> students = new ArrayList<>();
}
```

Here, a join table called `student_course` is created, with `student_id` as a foreign key to `Student` and `course_id` as a foreign key to `Course`. `Student` is the owning side, and `Course` uses `mappedBy = "courses"` to reference the field in `Student`.

- The default fetch type is **LAZY**.
- The join table is created automatically, unless you want a separate mapping entity.
- You can also use a custom join entity if you need to store extra data on the relationship itself.
- Prefer `PERSIST` and `MERGE` for cascading here, and avoid `REMOVE` unless you're certain of its effect.

## 3.10 Fetch Types

In JPA, `FetchType` defines *when* related entities (associations) are loaded from the database.

| Fetch Type | Description |
|---|---|
| `EAGER` | Loads the related entity immediately, along with the main entity |
| `LAZY` | Loads the related entity only when it's accessed (on demand) |

### 3.10.1 `FetchType.LAZY`

- The default for `@OneToMany` and `@ManyToMany`.
- The association is only loaded when it's actually used.

```java
Student s = studentRepo.findById(1L);  // department is NOT fetched yet
Department dept = s.getDepartment();   // department is fetched NOW (when accessed)
```

- Behind the scenes, Hibernate uses proxy objects.
- A `LazyInitializationException` can occur if you try to access a lazily loaded field after the session has already closed.

### 3.10.2 `FetchType.EAGER`

- The default for `@ManyToOne` and `@OneToOne`.
- The association is loaded immediately, along with the main entity.

```java
Student s = studentRepo.findById(1L);  // department is fetched IMMEDIATELY
```

**Downsides:**
- Causes unnecessary joins.
- Can lead to performance bottlenecks, especially with collections.
- Can trigger N+1 query problems.

**EAGER vs. LAZY:**

| Feature | EAGER | LAZY |
|---|---|---|
| Load timing | Immediate, with the main entity | On-demand, when accessed |
| Performance | Can be costly (too much data at once) | Better control over loading |
| Default for | `@ManyToOne`, `@OneToOne` | `@OneToMany`, `@ManyToMany` |
| N+1 problem risk | High, if not managed carefully | Also risky, if accessed inside a loop |
| Best practice | Use only when necessary | Preferable in most cases |

## 3.11 Sessions and Transactions

> **Note:** Once a method annotated with `@Transactional` finishes, the underlying session is closed.
>
> If you don't use `@Transactional` explicitly: in Spring Boot with Spring Data JPA, you might not need to. Spring Data automatically manages transactions for repository methods — it opens a session, starts a transaction, and closes it once the repository method finishes.

**Session open/close behavior:**

| Operation | Session Starts | Session Ends |
|---|---|---|
| A repository call (e.g., `findById`) | Start of the method | End of method execution |
| Manual `@Transactional` | Start of the method | End of method execution |
| `open-in-view: true` | Start of the HTTP request | End of response rendering |

## 3.12 The N+1 Problem

Suppose you want to fetch a list of `Student`s, and each student has a `Department` (`@ManyToOne(fetch = LAZY)`):

```java
List<Student> students = studentRepository.findAll();
for (Student s : students) {
    System.out.println(s.getDepartment().getName());
}
```

Here, there's **1 query** to fetch all students, plus **N additional queries** (one per student) to lazily fetch each department. So for 100 students, that's 101 SQL queries total — the "N+1 problem."

### 3.12.1 Solution: `JOIN FETCH`

`JOIN FETCH` tells JPA to fetch the related entity eagerly, using a single query with a `JOIN`.

```java
@Query("SELECT s FROM Student s JOIN FETCH s.department")
List<Student> findAllWithDepartment();
```

This runs only **one** query, performing an `INNER JOIN` to fetch students together with their departments.

**SQL behind the scenes:**

```sql
SELECT s.*, d.* FROM students s JOIN departments d ON s.department_id = d.id;
```

**When to use `JOIN FETCH`:**
- You're going to access related fields.
- You're seeing `LazyInitializationException`.
- You want a performance optimization.
- You want full control over the joins performed.

> **Note:** `JOIN FETCH` only works in JPQL (`@Query`), not in method-name-derived queries. Avoid stacking multiple `JOIN FETCH` clauses on collections — it can cause a Cartesian-product explosion:
>
> ```sql
> SELECT s FROM Student s
> JOIN FETCH s.department
> JOIN FETCH s.courses
> ```

### 3.12.2 Solving the N+1 Problem with `@EntityGraph`

`@EntityGraph` is a JPA annotation that lets you declare which related entities to fetch eagerly, without writing JPQL or using `JOIN FETCH`. It's a declarative way to optimize your fetching strategy and avoid the N+1 problem.

```java
@Entity
public class Student {
    @Id Long id;
    String name;

    @ManyToOne(fetch = FetchType.LAZY)
    Department department;
}
```

**Default behavior** (without `@EntityGraph`):

```java
List<Student> students = repo.findAll();
// accessing getDepartment() later causes N+1
```

**Using `@EntityGraph`:**

```java
public interface StudentRepository extends JpaRepository<Student, Long> {

    @EntityGraph(attributePaths = "department")
    List<Student> findAll();
}
```

This tells Spring: when fetching `Student`, also fetch `department` in the same SQL query.

**SQL behind the scenes:**

```sql
SELECT s.*, d.*
FROM students s
LEFT JOIN departments d ON s.department_id = d.id
```

You can go nested — `@EntityGraph(attributePaths = { "department.faculty" })` — and target multiple attributes at once — `@EntityGraph(attributePaths = { "department", "courses", "advisor" })`.

### 3.12.3 `JOIN FETCH` vs. `@EntityGraph`

Both solve the N+1 problem by eagerly loading related entities, but they differ in how and where they're used.

| Feature | `JOIN FETCH` | `@EntityGraph` |
|---|---|---|
| Works in JPQL | Yes | No |
| Works in derived queries | No | Yes |
| Pagination support | Problematic (with collections) | Safe |
| Clean separation | Mixed in with query logic | Declarative and clean |
| Complex join support | Yes | Limited |

## 3.13 Cascading in JPA

Cascading is a mechanism that lets one entity operation (like save or delete) automatically propagate to related entities. It applies mainly to relationships like `@OneToOne`, `@OneToMany`, and so on.

**Without cascading**, you must manually persist or remove child entities:

```java
Student student = new Student();
Address address = new Address();
student.setAddress(address);

// You must save both
entityManager.persist(address);
entityManager.persist(student);
```

**With cascading**, you only persist the parent — JPA handles the rest:

```java
@Entity
public class Student {
    @OneToOne(cascade = CascadeType.PERSIST)
    private Address address;
}

Student student = new Student();
student.setAddress(new Address());

// Only persist the student
entityManager.persist(student); // the Address gets saved too!
```

**Cascade types:**

| `CascadeType` | Description |
|---|---|
| `PERSIST` | When the parent is persisted, the child is persisted |
| `MERGE` | When the parent is merged (updated), the child is merged |
| `REMOVE` | When the parent is removed, the child is removed |
| `DETACH` | When the parent is detached from the persistence context, so is the child |
| `REFRESH` | Refreshes the child when the parent is refreshed |
| `ALL` | Includes all of the above |

**`@OneToMany` with multiple cascade types:**

```java
@OneToMany(mappedBy = "student", cascade = {CascadeType.PERSIST, CascadeType.MERGE})
private List<CourseRegistration> registrations;
```

Here: when a student is saved, their registrations are saved; when a student is updated, their registrations are updated; but deleting a student will **not** delete their registrations.

## 3.14 Transaction Management in Spring

A transaction is a set of operations that should execute as a single unit — either all of them succeed, or none of them take effect (atomicity).

**Example** — transferring money: deduct from Account A, then add to Account B. If the second step fails, the first must be rolled back.

### 3.14.1 The `@Transactional` Annotation

- `@Transactional` manages transaction boundaries automatically.
- **Where to use it:** the service layer is the most common and recommended place. It can be applied at the method or class level.

```java
@Service
public class UserService {

    @Transactional
    public void registerUser(User user) {
        userRepository.save(user);
        emailService.sendWelcomeEmail(user.getEmail()); // if this fails, the DB insert rolls back
    }
}
```

If any exception occurs, the entire transaction rolls back — the user won't be saved.

- Repositories already participate in the transaction created by the service, so you usually don't need `@Transactional` there, unless you're doing something custom.
- By default, Spring only rolls back on **unchecked** exceptions (`RuntimeException`, `Error`). To roll back on checked exceptions too, use:

```java
@Transactional(rollbackFor = Exception.class)
public void saveWithFileUpload(User user) throws IOException {
    userRepository.save(user);
    fileService.uploadFile(user.getProfileImage()); // throws a checked exception
}
```

- Use `@Transactional(readOnly = true)` to optimize read-only operations.

## 3.15 Projections

By default, `JpaRepository` returns entire entities, even if you only need two or three fields. This causes:
- Unnecessary joins
- Higher memory usage
- Possible `LazyInitializationException`s

**Projections** solve this by letting you fetch only the required columns directly from the database.

### 3.15.1 Interface-Based Projections

You define an interface with getters matching the entity's fields (or aliases in JPQL).

```java
public interface UserSummary {
    String getUsername();
    String getEmail();
}

public interface UserRepository extends JpaRepository<User, Long> {
    List<UserSummary> findByActiveTrue();
}
```

- Spring auto-generates a proxy-based projection and maps fields directly from the query results.
- Works with native queries, JPQL, and derived queries.
- Faster than DTO mapping, since there's no constructor call involved.

### 3.15.2 Class-Based (DTO) Projections

You define a DTO with a matching constructor.

```java
public class UserDTO {
    private final String username;
    private final String email;

    public UserDTO(String username, String email) {
        this.username = username;
        this.email = email;
    }

    // Getters...
}
```

- Requires a custom `@Query` for class-based projections.
- The constructor's parameter order and types must match the JPQL `SELECT new` clause exactly.

```java
@Query("SELECT new com.example.dto.UserDTO(u.username, u.email) FROM User u WHERE u.active = true")
List<UserDTO> findActiveUsers();
```

**Use DTO projections when:**
- You want immutable data.
- You need to add logic, formatting, or transformation.
- You want to avoid proxy objects.
- You want to use the projection outside of JPA (e.g., over the wire, in a REST response).

## 3.16 Paging and Sorting

Paging and sorting let you load data page by page, sort results, and combine both with custom queries — reducing memory usage (fetching 10 records instead of 10,000), supporting frontend pagination (tables, infinite scroll), and helping your application scale.

### 3.16.1 `Pageable` and `PageRequest`

Spring provides the `Pageable` interface and the `PageRequest` implementation to support pagination.

```java
public interface ProductRepository extends JpaRepository<Product, Long> {
    Page<Product> findByCategory(String category, Pageable pageable);
}

// In the service
Pageable pageable = PageRequest.of(0, 5); // page 0 (first), 5 items per page
Page<Product> page = productRepository.findByCategory("electronics", pageable);
```

The returned `Page` object offers `.getContent()` (the list of results), `.getTotalPages()`, `.getTotalElements()`, `.isFirst()`, and `.isLast()`.

### 3.16.2 Sorting with `Sort`

You can also sort explicitly using the `Sort` class:

```java
Sort sort = Sort.by("price").descending();
Pageable pageable = PageRequest.of(0, 10, sort);
```

### 3.16.3 Pagination with Custom Queries

If your query is custom, you must return a `Page<T>` and provide a `countQuery` for the total row count.

**JPQL example:**

```java
@Query(
  value = "SELECT p FROM Product p WHERE p.category = :category",
  countQuery = "SELECT COUNT(p) FROM Product p WHERE p.category = :category"
)
Page<Product> findByCategoryCustom(@Param("category") String category, Pageable pageable);
```

**Native SQL example:**

```java
@Query(
  value = "SELECT * FROM products WHERE category = :category",
  countQuery = "SELECT COUNT(*) FROM products WHERE category = :category",
  nativeQuery = true
)
Page<Product> findByCategoryNative(@Param("category") String category, Pageable pageable);
```

| Feature | Description |
|---|---|
| `Pageable` | Interface describing paging and sorting |
| `PageRequest` | Implementation of `Pageable` |
| `Sort` | Chainable object for defining sort order |
| `Page<T>` | Paginated result, with metadata |
| Custom queries | Require a `countQuery` for total-page calculation |

## 3.17 Best Practices in Spring Data JPA

1. **Avoid the N+1 select problem.** This occurs when JPA loads a parent entity and then lazily loads each of its children in separate queries (1 query + N additional queries):

   ```java
   List<Department> departments = departmentRepository.findAll();
   for (Department dept : departments) {
       System.out.println(dept.getEmployees().size()); // triggers N queries
   }
   ```

   Solve it with `JOIN FETCH` in JPQL, or with `@EntityGraph`.

2. **Use DTO projections for performance.** Don't fetch entire entities when only specific fields are needed — use interface-based or class-based (DTO) projections. This improves performance, reduces serialization issues in REST APIs, and is especially useful for public-facing APIs.

3. **Define proper transactional boundaries.** Keep read-only transactions clean with `@Transactional(readOnly = true)`. Annotate only the service layer, not the repository. Avoid long-running or overly broad transactions, and don't put heavy logic inside them.

4. **Use fetch joins effectively.** When you know you'll need child entities, use `JOIN FETCH` or `@EntityGraph` to fetch everything in a single query — but avoid doing this on very large collections, since it can cause memory spikes.

5. **Use pagination with large datasets** to avoid loading huge result sets into memory.

6. **Prefer DTOs in REST APIs** — avoid exposing JPA entities directly.

7. **Avoid bidirectional relationships unless needed** — they complicate serialization, especially in REST APIs.

8. **Use `@Transactional` carefully** — nested or misused transactions can lead to subtle bugs.
